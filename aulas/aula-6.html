Worktrees: cópias para testar sem medo

Você consegue pedir uma cópia de trabalho do projeto, testar nela e decidir se junta ao original ou descarta.

Pedir uma mudança grande direto no projeto original é teste sem volta. Se ficar ruim, você nem lembra mais como era antes. Esta aula mostra o jeito organizado de testar numa cópia. Para um texto solto quase nunca é preciso; para mudança grande no que está em uso, é o que dá segurança.

Em 1 minuto

  1. Uma worktree é uma cópia de trabalho ligada ao original.
  2. O original se chama main. A cópia trabalha numa linha paralela.
  3. Gostou? Peça para juntar, vendo antes o que muda. Não gostou? Descarte.

1Teste no original não tem volta

Quando o Codex mexe direto nos arquivos do projeto, a mudança vale na hora. Se o resultado ficar estranho, o jeito antigo já se foi.

Jorge tem uma página simples da loja, na pasta loja-jorge/site, que os clientes já usam. Ele quis cores novas e um menu diferente. Compare as duas vezes que ele pediu.

2Worktree é uma cópia ligada ao original

Copiar a pasta na mão ("site-copia", "site-copia2") vira bagunça rápido. O Git faz isso de forma organizada.

Ele guarda o histórico, isto é, as versões salvas da pasta. E cria uma worktree: outra pasta de trabalho, ligada ao mesmo histórico. Como as duas se conhecem, dá para levar só as mudanças boas da cópia para o original depois.

Na loja do Jorge, a cópia ficou no mesmo computador, numa pasta ao lado do projeto.

3main é o original; o resto é linha de teste

Toda worktree trabalha numa branch. Pense numa linha de metrô: a main é a linha que todo mundo usa. A branch é um ramal que sai dela para testar uma estação nova.

Se o teste der certo, o ramal volta para a linha principal. Se não der, ele é desativado e a main nem percebe.

Paula abriu o aplicativo e viu "main" e outro nome que não conhecia ao lado do projeto dela. O Codex tinha criado uma cópia sozinho para trabalhar em paralelo. Nada estava errado.

Apareceu um nome que você não pediu?

Pergunte ao Codex: "para que serve esta cópia e em que linha ela está?". Ele explica em uma frase. Várias worktrees listadas costumam ser só trabalho em paralelo.

4Teste na cópia, depois junte ou descarte

No aplicativo, ao começar uma conversa, existe a opção de trabalhar numa nova worktree local. Ela fica perto da caixa de mensagem. O nome do botão pode mudar entre versões.

Para levar o resultado ao original, peça ao Codex. O cuidado é um só: ele mostra o que vai mudar antes de juntar.

Jorge gostou do visual novo na cópia. Antes de pôr no ar, pediu para ver o que mudaria.

Se travou aqui, é normalSe o Codex disser que a pasta não usa Git, peça: "ative o Git nesta pasta e salve uma primeira versão". Se ele avisar de um conflito, é porque o original também mudou no mesmo trecho: peça que explique e pergunte a você como resolver.

O que você vê na interface

  1. main (ou master, em projetos mais antigos): a linha principal, o original. Não precisa se preocupar.
  2. Outro nome de linha: uma linha paralela de teste. Se você não pediu, pergunte ao Codex para que serve.
  3. Várias cópias listadas: trabalho em paralelo. O Codex às vezes cria sozinho.

Quando você não precisa disso

A worktree nasceu para projetos feitos em equipe, com várias pessoas ou vários agentes mexendo no mesmo material ao mesmo tempo. Para um texto, um e-mail ou um post, quase nunca é preciso.

Na prática

Se a Paula quer testar outro tom numa proposta, basta pedir: "crie uma versão nova em outro arquivo e não mexa na original". Salvar como versão nova já resolve.

Use quando

  1. A mudança é grande e pode quebrar algo que está em uso.
  2. Você quer comparar duas ideias, uma de cada vez.
  3. Vários agentes vão mexer no mesmo projeto ao mesmo tempo.
